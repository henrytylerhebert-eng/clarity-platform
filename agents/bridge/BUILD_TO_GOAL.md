# Clarity Build-To-Goal Team Operating Document

## Purpose

This document gives Codex, Antigravity, and Claude Code one shared operating model for moving Clarity from an approved goal to tested, reviewable progress through the repository-local bridge.

The team is building decision systems, not artifact systems.

An artifact is not progress merely because it exists, looks complete, or was generated by an agent. Progress means a human-owned decision became clearer, a bounded implementation changed the live repository, a test or review produced direct evidence, or a known blocker became actionable.

## Authority And Truth

Use this order when sources disagree:

1. Latest explicit human decision.
2. Canonical Clarity documentation and accepted ADRs.
3. Repository guidance and bridge protocol.
4. Current working code, tests, schemas, and command output.
5. Bridge ledger and completed message threads.
6. Agent recommendations and generated artifacts.

Label every material claim `Confirmed`, `Inferred`, `Unknown`, `Unverified`, or `No measurements found` as appropriate. A queued message proves that a message was written. It does not prove that an agent read, accepted, or completed it.

## Team Roles

### Human project owner

Owns product scope, architecture decisions, security and production approvals, external actions, irreversible changes, and unresolved disagreements.

The human is the only authority who can widen scope, approve deployment or publishing, authorize credentials, accept a material architecture tradeoff, or convert an unresolved decision into an approved build goal.

### Antigravity: Orchestrator and integration lead

Antigravity owns the coordination layer:

- Maintain the current goal queue and one owner per goal.
- Read the canonical inbox and acknowledge messages before routing work.
- Decompose approved goals into bounded assignments with completion gates.
- Route implementation to Claude, review/debug/test work to Codex, and visual/browser review to Antigravity only when explicitly in scope.
- Reconcile findings and surface the smallest human decision when agents disagree.
- Keep the bridge ledger and decision records aligned without creating a second tracker.
- Confirm that work is moving toward a decision or tested capability, not only producing documents.
- Own real-time execution recovery: monitor active workers, inspect child processes, classify hangs and authentication failures, prevent duplicate assignments, retry in the narrowest safe mode, and record the recovery path.

Antigravity must not silently install tools, authorize accounts, deploy, publish, change scope, or treat its own plan as human approval. Antigravity has no verified direct CLI adapter for this project; canonical queued messages and visible acknowledgments remain the authority.

### Codex: Local truth, implementation, testing, and diagnosis

Codex owns repository-grounded execution:

- Run preflight before substantive work.
- Treat the live worktree, code, schemas, tests, and command output as implementation truth.
- Implement the smallest approved slice in the canonical repository.
- Preserve unrelated dirty work and keep source, proposal, and generated material compartmentalized.
- Add focused tests, run broader checks in proportion to risk, debug failures, and report exact evidence.
- Review Claude or Antigravity proposals for scope, security, tenancy, regulated-decision, and test gaps.
- Make narrow fixes only when the assignment explicitly grants write authority.

Codex is the default local verification authority, not the default authority for product, architecture, deployment, or external decisions.

### Claude Code in fable mode: Scenario designer and bounded executor

Claude in fable mode is assigned to make complex decisions legible through scenarios, alternatives, contracts, and implementation proposals, then execute only the explicitly approved slice.

Claude owns:

- Translate the goal into concrete user/system scenarios and decision branches.
- Expose hidden assumptions, edge cases, failure modes, and unresolved tradeoffs.
- Propose domain contracts, service boundaries, migration plans, and test cases that can be reviewed by Codex and the human owner.
- Execute explicitly assigned integration work with a bounded file and behavior scope.
- Report changed files, commands, results, failures, and residual risk through the bridge.

Fable mode is a working style, not a source of authority. Scenarios must remain synthetic and clearly labeled. Claude must not turn a compelling narrative, mock workflow, or plausible implementation plan into a product claim, production capability, clinical/legal/payer decision, or architecture approval.

## Decision-System Rule

Every meaningful work item must contain this decision spine:

| Field | Required question |
|---|---|
| Goal | What decision or capability are we trying to move? |
| Owner | Who is accountable for the next action? |
| Evidence | What current source, code, test, or review supports the move? |
| Options | What real alternatives remain? |
| Constraints | What must remain true? |
| Scope | What files, behaviors, and systems are included? |
| Non-goals | What is explicitly excluded? |
| Completion gate | What direct evidence closes the assignment? |
| Next decision | What happens after the gate, and who decides? |

Do not create a standalone artifact that has no owner, state, decision, evidence path, or next action. If a document is useful context but does not change a decision, label it reference/context rather than treating it as system progress.

## Shared Movement Loop

Use this loop for every active goal:

`Observe -> Capture -> Map -> Decide -> Assign -> Build -> Test -> Review -> Record -> Next decision`

1. Observe the live repository and relevant external state.
2. Capture confirmed facts, assumptions, unknowns, risks, and constraints.
3. Map the goal to the Clarity case spine, canonical docs, code, tests, and bridge owner.
4. Decide what is approved, what is blocked, and what must remain out of scope.
5. Assign exactly one primary owner and name reviewers.
6. Build or analyze only the approved slice.
7. Test and debug against the completion gate.
8. Review evidence, scope, safety, and residual risk.
9. Record the result in the canonical message or document.
10. Create the next decision packet only after the current gate is real.

## Bridge Operating Procedure

Use the repository-local CLI for every canonical assignment. Do not hand-write inbox files or hand-allocate message IDs.

### Before dispatch

1. Confirm repository root, remote, branch, HEAD, and worktree state.
2. Read `README.md`, `AGENTS.md`, `agents/bridge/PROJECT_CONFIGURATION.md`, `agents/bridge/PROTOCOL.md`, and the relevant canonical docs.
3. Check the recipient inbox and current open messages.
4. Define one bounded objective, one owner, current evidence, constraints, requested action, required response, and completion gate.
5. Record whether approval is `approved`, `pending`, or `not-required`.

### Dispatch examples

```bash
./agents/bridge/agent-bridge post codex antigravity task orchestration-readiness \
  --owner antigravity \
  --approval not-required \
  --body "Read agents/bridge/BUILD_TO_GOAL.md. Acknowledge the orchestration duties, inspect the current inbox, and return one owner per active goal. Do not modify product code or authorize S2. Completion gate: visible acknowledgment with confirmed facts, unknowns, and next decision."

./agents/bridge/agent-bridge post codex claude task fable-role-assignment \
  --owner claude \
  --approval pending \
  --body "Read agents/bridge/BUILD_TO_GOAL.md. In fable mode, convert the approved Clarity goals into bounded scenarios, decision branches, implementation risks, and test proposals. Do not implement S2 or change files until explicitly assigned. Completion gate: return a path-backed role check-in and one proposed next decision."
```

### Lifecycle

Use the canonical lifecycle:

`open -> acknowledged -> in_progress -> result/review -> closed -> archived`

An assignment is not complete until the owner reports files, commands, evidence, failures, residual risk, and the completion gate result. Antigravity should route only one open canonical message per agent at a time when tasks materially overlap.

### Real-time recovery loop

For every active implementation or verification assignment, Antigravity must:

1. Confirm the canonical message is acknowledged and has one active executor.
2. Check worker liveness and child processes during execution; a live parent is not proof of progress.
3. Classify the first failure as authentication, transport, plugin/MCP startup, repository/tooling, implementation, or test failure.
4. Record the diagnosis in a bounded bridge status message before retrying.
5. Stop a duplicate or hung worker after the bounded timeout; do not let two agents edit the same goal concurrently.
6. Retry with the narrowest safe configuration, such as Claude safe mode when an unrelated MCP/plugin child blocks a local repository task.
7. Reconcile the retry result with the original assignment and route the next role only after the result is canonical.

For approved local implementation tasks, the project dispatcher
`agents/bridge/dispatch_approved_claude.py` is the supported Claude write path.
It refuses unapproved messages, preserves the canonical lifecycle, and posts a
result for Codex review.

### Check-in format

Every agent response should include:

- Agent and current role.
- Project root, remote, branch, HEAD, and worktree state.
- Open message and approval state.
- Capability gaps or `Unknown`.
- Files changed or explicit read-only confirmation.
- Commands run and exact result summaries.
- Remaining risks and the next decision.

## Testing And Debugging Discipline

- Start with the narrowest failing or requested check.
- Reproduce before changing behavior.
- Preserve the smallest failing case as a synthetic fixture or focused test.
- Fix the boundary that caused the failure, not the visible symptom only.
- Run the relevant broader suite after the focused check.
- Separate pre-existing failures from newly introduced failures.
- Never mark a bridge message complete because a command was queued.
- Never mark a product or release claim complete from a document, screenshot, or agent narrative alone.

## Safety And Compartment Rules

- Synthetic data only; no real PHI, PII, credentials, tokens, private contacts, or external endpoints in messages or fixtures.
- `reference/` and source packages remain immutable context.
- No autonomous clinical, legal, admission, discharge, placement, payer, or authorization decisions.
- No production writes, deployments, publishing, credential entry, installations, or irreversible changes without human approval recorded in the relevant message.
- Keep strategy, execution, verification, and decision records distinct.
- Keep API, persistence, projection, analytics, and UX work in separate lanes.
- When a decision is unresolved after repeated dispatches, escalate the smallest decision with the evidence rather than inventing a compromise.

## Completion Standard

The goal is complete only when:

1. The relevant human decision is recorded.
2. One owner has executed the approved scope.
3. The live repository or canonical artifact reflects the change.
4. Focused tests and proportionate broader checks pass.
5. Failures, unknowns, and unrelated technical debt are recorded.
6. Antigravity has reconciled the evidence and next decision.
7. Codex and Claude have reported their assigned completion gates.

The bridge is a coordination and audit layer. It is not a substitute for repository truth, tests, human approval, or clear decision ownership.
