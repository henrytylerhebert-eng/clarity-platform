# Source-to-Canonical Mappings

**Status:** Proposed and unverified. Validate every path, field name, enum, and ownership rule against the live `clarity-platform` working tree before implementation.

## 1. Purpose and authority

This document prevents an adapter, migration, or projector from inventing a second system of record. The repository implementation remains the highest-authority source. The reporting SQL blueprint is a reporting proposal, not a canonical transactional schema. The excluded legacy workbook is not a source of record and is not an approved ingestion source.

The canonical path is:

```text
source-owned fact
  -> authenticated command or controlled adapter
  -> canonical operational aggregate
  -> immutable governed event + audit + delivery record in the same transaction
  -> replay-safe operational projection
  -> de-identification/tokenization transformation
  -> tenant-scoped mart fact
  -> versioned metric snapshot
```

No mapping may bypass the operational command boundary for a native Clarity fact, and no browser may write a fact or metric directly.

## 2. Mapping status vocabulary

| Status | Meaning |
|---|---|
| `Confirmed` | The handoff proves the source concept exists in the repository or canonical documentation. Exact runtime shape still requires repository preflight. |
| `Inferred` | The mapping follows an existing pattern but its exact source model was not included in the snapshot. |
| `Proposed` | New canonical entity/event/adapter behavior for this module. |
| `Unknown` | The source, identifier, vocabulary, or operational authorization is not established. |
| `Needs decision` | Owner/security/privacy/clinical governance must select or approve the rule before code or data migration. |

## 3. Canonical identity and scope mapping

| Canonical field | Native Clarity source | External source | Rule | Status |
|---|---|---|---|---|
| `organizationId` | authenticated actor and organization-scoped case predicate | adapter configuration plus source-tenant mapping | Never trust a browser or inbound payload to expand scope. The server resolves and validates the organization. | Confirmed pattern; proposed adapter contract |
| `facilityId` | accepted facility response / receiving destination | versioned facility crosswalk | Must belong to `organizationId` and be effective at `effectiveAt`. Unknown mappings are quarantined. | Proposed |
| `programId` | accepted program / receiving program | versioned program crosswalk | Required for the first slice unless Tyler approves facility-only episodes. | Needs decision |
| `unitId` | receiving unit when known | versioned unit crosswalk | Nullable at admission; later placement events must not rewrite the admission destination. | Proposed |
| `caseId` | existing case aggregate | source case reference only when contractually mapped | Case remains owned by Case and Access. It is a linkage, not an analytics identifier. | Confirmed boundary |
| `episodeId` | created by episode service during admission handoff | generated by Clarity after source identity reconciliation | Never use an external encounter number as the canonical primary key. | Proposed |
| `episodeDayId` | generated deterministically or stored on first materialization | none accepted directly | Unique by organization, episode, and facility-local service date. | Proposed |
| `personToken` | HMAC/tokenization service over an approved canonical person key | approved master-person mapping | Never a raw MRN, name, DOB, SSN, or reversible database ID. Not returned in aggregate APIs. | Needs security/privacy decision |
| `payerToken` | payer master key transformed for mart use | versioned payer crosswalk | Raw payer references and portal identifiers stay in the PHI operational store. | Proposed |

## 4. Existing case/access concepts to post-admission mappings

These mappings preserve ownership. They do not move pre-admission records into the episode aggregate.

| Existing concept | Canonical post-admission use | Governed event | Ownership and constraints | Classification |
|---|---|---|---|---|
| Accepted facility response | Admission handoff prerequisite and receiving-scope reference | `CASE_ADMISSION_HANDOFF_COMPLETED.v1`; correlated `EPISODE_CREATED.v1` and `ADMISSION_RECORDED.v1` | Case owns the acceptance. Episode stores only immutable source references and the admitted destination fact. | Confirmed source; proposed events |
| Case overall/workstream status | Handoff validation and historical context | no generic status-copy event | Do not copy the case state machine into episode state. Handoff records source case version. | Confirmed boundary |
| Pre-admission authorization preparation/outcome | Optional source reference for a new episode authorization lifecycle | `EPISODE_AUTHORIZATION_OPENED.v1` | Pre-admission readiness remains case-owned. Post-admission concurrent review is episode-owned. No automatic payer decision is inferred. | Confirmed distinction; proposed link |
| Coverage/eligibility/benefit verification | Payer/plan context and unresolved-question references | source reference in authorization event; later dedicated events if approved | Do not flatten evidence, representative notes, or unresolved questions into aggregate metrics. | Confirmed source pattern; proposed use |
| Packet version | Provenance reference for the admission handoff | `CASE_ADMISSION_HANDOFF_COMPLETED.v1` and `ADMISSION_RECORDED.v1` payload references | Do not copy packet contents into the event or mart. | Proposed |
| Transport/custody event | Optional evidence that the operational handoff occurred | source reference only | Admission recording must follow the facility's governing process; Clarity does not autonomously declare admission from transport telemetry. | Confirmed policy; proposed mapping |
| Current frontend analytics event seam | No direct migration into canonical event history | none by default | Treat as prototype telemetry. Only backfill after event-by-event provenance, tenant, semantics, and duplicate review. | Confirmed limitation |

## 5. Initial native workflow command mappings

### 5.1 Admission-to-episode handoff

| Command input | Canonical write | Event field/payload | Validation |
|---|---|---|---|
| route case ID | `CaseEpisodeLink.caseId` | `subject.caseId`; `payload.sourceCaseId` | Case belongs to actor organization and expected case version matches. |
| accepted response ID | `AdmissionRecord.sourceAcceptanceId` | `payload.acceptedFacilityResponseId` | Response belongs to case and represents an accepted destination under existing policy. |
| receiving facility/program/unit | `Episode` and `AdmissionRecord` scope | tenant fields and admission payload | IDs belong to the same tenant and actor has handoff capability for destination scope. |
| admitted timestamp | `Episode.admittedAt`, `AdmissionRecord.admittedAt` | `occurredAt`, `effectiveAt`, `payload.admittedAt` | ISO timestamp; not future beyond approved tolerance; translated to facility-local `serviceDate`. |
| facility timezone | immutable admission timezone plus current facility dimension | `payload.facilityTimezone` | Must be an approved IANA zone. Do not silently default to `America/Chicago`. |
| packet/custody/transport references | `AdmissionRecord` source references | payload IDs only | Same case/organization; nullable; no source text. |
| actor attestation | `AdmissionRecord.attestationTextVersion` and audit | `review.status=ATTESTED` | Human or authorized service records a fact; no clinical appropriateness inference. |
| command metadata | existing idempotency/audit plus governed event | envelope correlation/causation/command fields | Idempotency key and expected version are required. |

Atomic outcome: case-owned handoff history, new episode and admission records, immutable audit, governed events, and delivery rows commit together. A projector failure must not roll back the accepted command; it is retried from delivery state.

### 5.2 Authorization review

| Command input | Canonical write | Event mapping | Notes |
|---|---|---|---|
| episode authorization ID | `AuthorizationReview.authorizationId` | `payload.episodeAuthorizationId` | Optional only when a review is being used to open/link the authorization atomically under an approved command contract. |
| review type | `reviewType` enum | `payload.reviewType` | Controlled vocabulary; unknown external values are mapped to review-required quarantine, not `OTHER` silently. |
| requested/decided date ranges | review range fields | payload ranges | Inclusive date ranges; end cannot precede start. |
| outcome | `AuthorizationReview.outcome` | `payload.decisionStatus` | Human/source-reported payer state; Clarity does not choose the outcome. |
| approved/denied day decisions | one current `AuthorizationDayDecision` version per episode day | `AUTHORIZATION_DAY_DECISION_RECORDED.v1` | Day-level facts supersede aggregate day totals for analytics. Overlaps raise a data-quality issue. |
| due date | `reviewDueAt` | payload `dueAt` | Drives queue risk; source and timezone must be explicit. |
| payer reference/document reference | restricted operational fields | envelope provenance/source references | Never copied into the de-identified fact. |
| attestation | review status, actor, time | envelope review metadata | Draft reviews are excluded or pending review per metric policy. |
| correction | new review/decision version plus immutable correction event | correction block and supersedes ID | Original row/event remains accessible through audit and lineage. |

### 5.3 Documentation gap

| Command/rule input | Canonical write | Event mapping | Notes |
|---|---|---|---|
| episode/day scope | `DocumentationGap.episodeId` / optional day ID | subject and payload IDs | Scope must match tenant and facility/program/unit. |
| gap type | `gapTypeKey` from controlled registry | payload `gapType` | The registry identifies required evidence; it does not diagnose or make a clinical decision. |
| source | source type, rule version, document reference | provenance and payload source fields | Event contains references, never note text. |
| severity | controlled operational severity | payload severity | Human/rule classification for work ordering; not clinical acuity. |
| due date | `dueAt` | payload `dueAt` | Facility policy version must be traceable where rule-derived. |
| assignment/status | gap fields plus optional UR queue assignment | `DOCUMENTATION_GAP_STATUS_CHANGED.v1` | Resolving a gap requires permitted evidence/attestation; it does not rewrite a clinical note. |
| correction | new gap version/event | correction block | Material changes require reason and supersession. |

## 6. Reporting blueprint to canonical mapping

The supplied `SCHEMA_BLUEPRINT.sql` is useful as domain vocabulary but conflicts with the required architecture in several places.

| Reporting blueprint item | Canonical replacement | Reason/status |
|---|---|---|
| `patient_identity` in reporting schema | no identity table in `analytics`; restricted operational person boundary plus one-way `episodeToken`/`personToken` transformation | Proposed. Prevents raw PHI from sharing dashboard access. |
| `episode.patient_id` | operational episode-to-person boundary not included in mart; `analytics.fact_episode.episode_token` | Proposed. Token is scoped/keyed and not returned from aggregate endpoints. |
| `episode` as both operational and reporting record | `Episode` in Prisma operational store plus `analytics.fact_episode` projection | Proposed separation; avoids two writers/systems of record. |
| `admission_event` | immutable `ADMISSION_RECORDED.v1` plus `fact_episode`/future admission fact | Proposed. Native command is the source; event is the spine. |
| `discharge_event` | future `DISCHARGE_RECORDED.v1` and corrected episode-day projection | Later slice; discharge authorization and workflow remain human-governed. |
| `episode_day` | operational `EpisodeDay` plus `fact_episode_day_authorization` | Proposed first slice. Facility-local date and correction semantics are explicit. |
| `ur_authorization.requested_days/approved_days/denied_days` | `EpisodeAuthorization`, `AuthorizationReview`, and day-level `AuthorizationDayDecision` | Proposed. Aggregate totals cannot represent overlap, partial approval, correction, or which day is at risk. |
| `ur_authorization.denial_reason` free text | controlled denial/reason registry plus restricted source reference | Needs definition/governance. No free text in mart. |
| `payer` | operational payer/plan context plus tokenized `dim_payer` | Proposed. Crosswalk/version ownership remains unresolved. |
| `metric_snapshot` without definition/quality/suppression lineage | `metric_definition`, `recompute_run`, `metric_snapshot`, and restricted lineage tables | Proposed. Supports reproducibility and correction history. |
| implicit single-facility rows | organization + facility/program/unit scope on every fact/dimension | Proposed; required for tenant enforcement. |
| default timezone assumptions | facility-versioned IANA timezone | Needs decision for timezone change policy; no silent default. |

Every source profile is versioned, tenant-bound, and reviewed before activation. A profile contains:

### 7.1 Native Clarity events

- Source: controlled service command.
- Trust: highest after command authorization and invariant checks.
- Identity: canonical IDs generated/resolved by operational services.
- Dedupe: command idempotency plus aggregate version/event uniqueness.
- Correction: explicit domain correction command.
- Initial slice: active.

### 7.2 EHR FHIR/HL7

- Source: approved FHIR resources/subscriptions/bulk export or HL7 v2 messages.
- Trust: source-reported, not self-validating.
- Required adapter behaviors: source message hash, message control/resource version, sender, received time, patient/encounter reconciliation, code mapping, quarantine, acknowledgement, and replay.
- Appropriate later facts: ADT admission/discharge/transfer candidates, document metadata, selected observation/order references.
- Prohibited shortcut: an ADT message may suggest a fact but must not bypass reconciliation, tenant mapping, facility workflow policy, or human review where required.
- Initial slice: boundary only; not operationally required.

### 7.3 Payer systems/portal

- Source: payer API, clearinghouse, portal-assisted human entry, or approved batch.
- Required fields: payer source key, authorization reference, decision/effective times, day/range semantics, source version/hash, operator or service identity.
- Unknowns: payer availability, contracts, code systems, API rights, and whether automated retrieval is permitted.
- Initial slice: human-attested native entry; adapter boundary only.

### 7.4 Staffing/payroll

- Source: workforce/timekeeping/payroll export.
- Scope: Hospital Operations/Workforce, not required for UR slice.
- Required controls: employee tokenization, role/pay-code crosswalk, labor-period correction, aggregation policy, and workforce privacy review.
- Prohibited shortcut: no employee names or raw payroll detail in general executive analytics.

### 7.5 Batch import

- Source: signed/controlled CSV or other approved format.
- Landing: encrypted quarantine outside canonical tables.
- Validation: file checksum, template version, tenant/profile, row count, schema, referential scope, duplicate keys, enum/date validation, and PHI field allowlist.
- Promotion: row-level accepted/rejected manifest; authorized human approval where policy requires; canonical commands/events, not bulk SQL writes.
- Correction: a new import version or canonical correction event; never overwrite the prior file's accepted facts.

### 7.6 Human attestation

- Source: role-scoped operational form embedded in the normal workspace.
- Required metadata: actor, role/capability, purpose, organization/scope, attestation text/version, effective time, source method/reference, correlation, idempotency, and expected aggregate version.
- Design rule: capture the fact once where the work occurs; do not create a second “reporting form.”

## 8. External vocabulary mapping behavior

| Condition | Behavior | Metric eligibility |
|---|---|---|
| exact approved code mapping | accept and record mapping profile/version | per event policy |
| source value maps to controlled `UNKNOWN` with explicit semantics | accept as review-required only where the canonical contract permits `UNKNOWN` | `PENDING_REVIEW` or excluded |
| unmapped facility/program/unit | quarantine; no canonical event | ineligible |
| unmapped payer | operational review queue; payer dimension omitted until resolved if the fact can otherwise be safely accepted | dimension-specific metrics excluded/pending |
| unsupported status/outcome | quarantine or human mapping review | ineligible |
| source and canonical record disagree | preserve both provenance references; raise `SOURCE_DISAGREEMENT`; do not silently select one | pending/excluded under metric policy |
| duplicate source message | return/record duplicate outcome without new source event | original eligibility unchanged |
| late-arriving valid fact | append with source/effective/recorded times; recompute affected window | eligible after recomputation if quality passes |
| correction/reversal | append targeting one active source fact; recompute impact window | superseded version excluded; replacement evaluated |

## 9. De-identification mapping

| Operational field | Mart field | Transformation |
|---|---|---|
| `Episode.id` | `episode_token` | HMAC with environment-specific key, versioned key ID stored in restricted transformation metadata; no raw ID in mart. |
| `AuthorizationReview.id` | `review_token` | same approved tokenization service with type/domain separation. |
| `DocumentationGap.id` | `gap_token` | same approved tokenization service with type/domain separation. |
| facility/program/unit IDs | surrogate dimension keys | tenant-scoped slowly changing dimension lookup. |
| exact timestamps | date keys or approved coarse freshness metadata | retain exact event time only in operational/event store unless a metric requires and privacy approves it. |
| payer ID/reference | payer surrogate/token and category | reference/representative details excluded. |
| note/document text | no mart field | map only controlled gap/evidence type, status, age bucket, and source coverage. |
| actor/user ID | no fact field | operational audit only; workforce analytics requires a separate approved employee-token policy. |
| event IDs | restricted `analytics_lineage` only | not exposed to dashboard roles; used for audited reconstruction. |

## 10. Backfill mapping rules

1. Backfill only from an authoritative operational record or an approved, provenance-bearing external source.
2. Do not ingest the legacy workbook as canonical history.
3. Do not convert prototype frontend telemetry into source facts without owner approval and a mapping review.
4. Record a backfill run ID, code/mapping versions, source snapshot/hash, scope, row counts, rejects, actor approval, and source watermark.
5. Use deterministic dedupe keys. Re-running the same input/profile must not duplicate events or facts.
6. Mark backfilled events with `source.method=BATCH_IMPORT` or an explicit native backfill method and preserve original effective time separately from recorded time.
7. Apply the same authorization, tenancy, schema, correction, quality, and metric-eligibility rules as live ingestion.
8. Validate counts against source records; do not validate against a workbook formula as if it were canonical truth.
9. Keep first-slice synthetic fixtures in a distinct test/synthetic classification and database boundary.

## 11. Reconciliation outcomes

A reconciliation run returns only controlled outcomes:

- `MATCHED_NO_CHANGE`;
- `MATCHED_CORRECTION_REQUIRED`;
- `SOURCE_ONLY_REVIEW_REQUIRED`;
- `CLARITY_ONLY_REVIEW_REQUIRED`;
- `SOURCE_DISAGREEMENT`;
- `DUPLICATE_SOURCE_RECORD`;
- `TENANT_SCOPE_UNRESOLVED`;
- `FACILITY_MAPPING_UNRESOLVED`;
- `PROGRAM_MAPPING_UNRESOLVED`;
- `UNIT_MAPPING_UNRESOLVED`;
- `UNKNOWN_ENUM_MAPPING`;
- `PRIVACY_POLICY_BLOCKED`.

No reconciliation process automatically resolves a clinical, admission, discharge, authorization, legal, or placement decision.

## 12. Decisions required before mapping activation

1. Episode identity and whether one accepted case can create more than one episode.
2. Whether `programId` is mandatory at admission and how unit assignment is corrected.
3. Facility-local episode-day boundary, daylight-saving behavior, and timezone-version policy.
4. Approved payer and denial/reason vocabularies.
5. Person/episode token service, key custody, rotation, and re-tokenization plan.
6. Minimum required source evidence and attestation for each authorization outcome.
7. Late-arrival and correction recomputation windows.
8. Data-retention and purge behavior for source payload quarantine and lineage.
9. Whether any historical operational source is authoritative enough for production backfill.
10. Governance prerequisites for cross-organization cohorts or agency exports; neither is activated by this mapping.
